# ADR-006：SPEC 10.3（脚本解 Hose ≤ 1）的落地与 G4 返工方法

- 编号：ADR-006
- 标题：SPEC 10.3（脚本解 Hose ≤ 1）的落地与 G4 返工方法
- 日期：2026-10-14
- 状态：已接受

## 背景

SPEC v1.1 新增 10.2 预算上限阶梯与 10.3 脚本解质量要求（裁决
[`docs/owner-decisions/2026-10-14-g4-levels.md`](../owner-decisions/2026-10-14-g4-levels.md)）。
落地时遇到三处未写清之处：

1. SPEC 16.2 要求统计 `HoseTriggered` 事件数，但该事件由 `SfxPlugin` 在当帧取走（ADR-004 第 4 条），
   测试在帧结束后读不到。
2. SPEC 10.3 与裁决把需要重做的关卡列为 1-7 / 1-8 / 1-9（及 1-10），裁决同时写“1-1 ～ 1-6 不动”。
   实际回放发现 **1-3 的脚本解也用掉 2 个 Hose**（level_tick 14244 与 16275，后者清掉最后一个敌人，
   下一 tick 判胜），以前的 `docs/levels.md` 没有记录 1-1 ～ 1-3 的 Hose 用量，因此未被发现。
   以车道状态与 `sfx.hose` 音频请求两种方式独立统计，结果一致。
3. SPEC 10.2 只说“当前档位写不出合格脚本解时降一档”，没有定义“写不出”的判定。

## 决策

1. **Hose 计数**：`lane_defense_system` 发出 `HoseTriggered` 当且仅当把某条激活车道的
   `hose_available` 置为 false，且每条车道至多一次，因此测试以“激活车道中已用掉的 Hose 数”计数
   （`tests/common/mod.rs::hoses_used`），与事件数一一对应。不为测试改变事件的消费方式。
2. **1-3**：SPEC 10.3 的规则本身对每关成立（测试“对每关断言此条”），括号中的关卡列表是不完整的枚举。
   采用对“1-1 ～ 1-6 不动”影响最小的方案：**只重录 1-3 的脚本解，关卡 RON 不变**（1-3 的预算本就低于
   任何档位上限，降档对它没有意义）。1-4 的 golden 不受影响（golden 只回放 1-4）。
   若重录无法满足 10.3，则按 AGENT 3.5 停下提问——实际重录成功（Hose 1）。
3. **“写不出”的判定**：用 `scripted_levels.rs::search_plans` 对该关 3 套卡组 × 512 组机器人参数
   （共 1536 次录制，高于 AGENT 3.4 建议的 2 × 8）逐一录制；没有任何一次“胜利且 Hose ≤ 1”即判为
   当前档位不可解，降一档重新生成（`gen_levels.py --tier k`）。有合格结果时取排序第一的参数
   （Hose 少者优先，其次用时短）写入 `record_plan`，并在 `docs/levels.md` 记录档位与合格率。
4. **1-7 在第 1 档**：1-7 的原预算（最大 30 / flag 66）低于第 1 档上限，按第 1 档重新生成的 RON 与原文件
   逐字节相同；返工只体现为重新搜索卡组与参数、重录脚本解。

## 后果

- 每关在 `docs/levels.md` 有档位、Hose 用量与搜索合格率，合格率低的关卡（1-9、1-10）提示负责人试玩时重点关注。
- 搜索工具随仓库提交，任何人可复现每关的档位判定。

## 替代方案

- （1）在 FixedUpdate 末尾插入测试专用系统读取事件：需要改动 app 的系统注册，只为测试服务，否决。
- （2）把 1-3 视为“不动”并让测试跳过 1-3：违反 10.3“对每关断言”，否决；修改 1-3 的波次数据：
  超出必要范围，否决。
- （3）以固定少量参数（如 2 × 8）判定“写不出”：搜索很便宜（1536 次录制在 8 核上约 1 ～ 3 分钟），
  多搜一些能避免不必要的降档，否决。
